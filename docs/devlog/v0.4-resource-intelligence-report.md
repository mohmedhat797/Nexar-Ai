**Date:** 2026-10-01 · **Branch:** `feat/nexar-v0.4-resource-intelligence` (from `ebc1516`, the v0.3
merge) · **Decision:** [ADR-020](../adr/020-resource-intelligence-scheduler.md) · **Issues:** #18

## Verdict

The Resource Controller now has a second, versioned policy, `resource-intelligence@1`. It is
explainable, quota-aware, cost-aware and history-aware, and uses no machine learning.
`deterministic@1` is unchanged (its tests pass untouched) and stays the default until the owner sets
`routing.policy: "resource-intelligence"`.

- **Hard filters, then scoring.** Scoring only reorders candidates that passed every hard filter. A
  seeded invariant test (250 random cases) shows the eligible set always equals the hard-filter
  output, and a "perfect history" test for each of the 11 filters shows a score never re-admits a
  rejected resource.
- **Honest uncertainty.** Quota is `unknown` unless the owner declared an allowance (which Nexar then
  counts from its own telemetry) or a runtime reported a signal through a documented interface. No
  installed runtime has a supported, non-experimental quota API, so no vendor probe ships. Unknown
  quota is never treated as unlimited or as zero. Unknown cost under a strict limit is rejected.
- **Owner first.** Task, lane and task-kind preferences rank before any learned signal unless the
  owner opts into `preferences: "weighted"`.
- **Explainable.** `nexar route --explain` prints every candidate with its tier, each factor (value ×
  weight = contribution, with neutral or cold-start markers), quota, estimated cost and reasons. Every
  decision carries `name@version` and a `configId`.
- **Gate:** `pnpm check` passes with 1,796 tests (7 skipped; live tests are opt-in).

## What shipped

**Quota (NXR-030).** Observations carry provenance (`owner-declared`, `nexar-accounting`,
`vendor-reported`; `vendor-probe` is reserved) and are judged per decision as `known-current`,
`known-stale`, `unknown` or `exhausted`. Headroom is the minimum across a resource's windows. Owner
allowances (requests, tokens or USD over daily, weekly, monthly or rolling windows) are counted from
Nexar's own `execution.finished` records. Runs with unmeasured usage are counted as unaccounted, never
as zero. Claude Code's documented `rate_limit_event` and any adapter's `QUOTA_EXHAUSTED` failure
become vendor-reported observations, held for one hour when no reset time is given. Reservations keep
headroom for named task kinds or lane roles (`quota.reserved`, `quota.reserved-for-task`). With
`requireKnownQuota`, unknown or stale quota is rejected. `nexar resources` shows a `QUOTA` column.

**Cost (NXR-031).** `estimator@1` uses size metadata only (characters ÷ 4 of the prompt and system
prompt, requested output tokens). Per-token profiles give cash estimates. Subscriptions are
`subscription-allowance` (zero marginal cash, consumes allowance). Local compute and free resources
are zero. Unknown profiles and zero catalog rates are `unknown`. `maxCostUsd` rejects over-limit
candidates with the numbers in the reason (`cost.exceeds-limit`) and, by default, unknown cost
(`cost.not-estimable`). `ExecutionRecord.costEstimate` keeps the estimate, the actual, and the
absolute and relative error when both are known. Claude Code is the only runtime with a documented
budget flag, so only it receives `--max-budget-usd`.

**History scoring (NXR-032).** The history reader aggregates `execution.finished` records per
(resource, task kind) inside a 30-day window: successes, resource faults, timeouts, p50/p95 latency
of successful runs, and mean measured cost. Caller and policy outcomes (`VALIDATION_ERROR`,
`POLICY_REJECTED`, `CONFIGURATION_ERROR`, `APPROVAL_DENIED`, `SANDBOX_UNAVAILABLE`, cancellation,
unknown codes) are excluded. The factors are default, availability, auth, quota, cost, latency,
Laplace-smoothed success, and lane. Each is clamped to [0, 1] and weighted from config. Below
`minSamples` (default 5) history factors are neutral (0.5). If the policy throws, the controller
ranks with `deterministic@1` over the same hard-filter stage, stamps
`policy.fallback = { from, reason }` and logs a warning with codes only. Without a fallback it fails
closed.

**Engineering signals (NXR-034).** Engineering records are aggregated per (resource, lane role).
Implementer roles get first-round gate pass rate, rework rounds, review approvals and owner
approvals. The review role gets valid-verdict rate. A `request-changes` verdict counts against the
implementer, never the reviewer. The `lane` factor applies only when the task carries a lane role.

**Discovery (NXR-033).** Each native integration detects its own binary on `PATH` with a `stat` only:
`claude`, `codex`, `agy` and `dsh`, honouring `PATHEXT` on Windows. The pi integration lists the
pinned static catalog for an owner provider allowlist, with rates labelled `catalog`, and lists
owner-configured Ollama or OpenAI-compatible endpoints (no scanning, no redirects, 1 MiB and 200-model
bounds). The merge is deterministic: config wins, `excludeIds` are honoured, and the first source id
wins a cross-source collision. Results are cached with an injected clock. A failing or slow source
is reported (`failed`, error code only) and skipped. Discovered resources start `unknown` and are
probed like any other. Discovery is off for routing by default; `nexar resources --discovered`
always shows it with a per-source report and a `PROVENANCE` column.

## Live checks (real host, no paid task)

The v0.3 end-to-end state (two engineering runs plus 30 telemetry events) was copied and the policy
switched to `resource-intelligence` with `minSamples: 1`, because the real history has one sample per
resource.

1. **Discovery.** `nexar resources --discovered` probed the configured `claude-code` and `codex` as
   `available` / `authenticated` with quota `unknown`. The `claude` CLI was found on `PATH`
   (`cli:claude-code ok 1`) and skipped as a collision because config wins. `codex` is configured by
   binary path, not on `PATH` (`cli:codex ok 0`). `agy` and `dsh` are not installed. The catalog and
   endpoint sources were `disabled` (not configured).
2. **`nexar route --explain`** on the real environment ran no task:

   ```text
   Policy: resource-intelligence@1 (config fff6a76a21fb)
   Selected resource: claude-code
     1. claude-code: eligible, tier 1, score 0.706488
          latency 0.881549 × 0.1 = 0.088155 [p50=8062ms]
          success 0.666667 × 0.2 = 0.133333 [1/1]
          cost: subscription-allowance, $0.000000 …
     2. codex: eligible, tier 1, score 0.578326
          latency 0.599922 × 0.1 = 0.059992 [p50=40013ms]
   ```

3. **Historical factors from v0.3.** The execution history gives Claude Code 1/1 coding runs (p50 8.1 s,
   measured mean cost $0.0385) and Codex 1/1 (p50 40.0 s, cost not reported, so no cost sample). The
   lane history gives each resource one `feature` sample (both gates passed first time, approved on
   review; Codex also had one owner approval) and one valid `review` verdict. These are single
   samples: with the default `minSamples` of 5 every history factor is neutral, which is the intended
   cold-start behaviour.
4. **Optional engineering task:** not run, to avoid spending subscription allowance on a check the
   offline tests and the v0.3 records already cover.

## Bugs found and fixed during review

- A stale vendor "exhausted" signal without a reset time blocked a resource forever. It now becomes
  stale like any other vendor signal (`quota.ts`, with a regression test).
- The lane-history reader followed a symlinked task directory. Reads now use `lstat` on the directory
  and `O_NOFOLLOW` on the file.
- Local-endpoint discovery let a raw `TypeError` (refused redirect or unreachable host) escape instead
  of a Nexar error code. It is now `INTEGRATION_UNAVAILABLE` with no URL.
- Catalog discovery output followed raw catalog order. It is now sorted by resource id.
- `PATH` lookup (filesystem IO) had been placed in the zero-dependency `@nexar/contracts`. It was
  moved to `@nexar/resource-registry`.
- Four delegate tests asserted the wrong thing (`__proto__` is not a valid resource id; negative
  latency is correctly neutral; two invariant cases used a control candidate that was itself
  filtered). The tests were fixed; the policy was right.

## Deviations and notes

- **Process (ADR-009).** The scoring and discovery delegates stopped at the relay CLI's session limit
  after writing most source files but no tests, wiring or config. The orchestrator completed both
  units instead of waiting two hours. See [`ai-usage.md`](ai-usage.md).
- **Implementation choices** that ADR-020 left open (lane preferences at tier 3, weighted-mode
  semantics, lane factor only with a lane role, latency over successes, fallback stamp, discovery
  plumbing) are recorded in ADR-020's "Implementation notes".
- **`cost.not-evaluated`.** `deterministic@1` still emits it, by design (it is unchanged). The new
  policy evaluates cost.
- **The ACP process-group test** (`integrations/deepseek-harness/src/acp/acp.test.ts`, "kills the
  process group…") failed twice while three delegates and the suite ran at once. It passed 3/3 in
  isolation and in every full gate since. It is timing-sensitive under heavy load; v0.4 does not touch it.

## Unresolved items

- **Vendor quota probes.** Codex `account/rateLimits/read` is experimental and `agy /quota` is
  unverified, so neither ships ([research](../research/upstream/v0.4/upstream-refresh.md)). Revisit
  when either is documented as stable.
- **Real history is thin.** Until there are at least 5 samples per (resource, task kind) or lane role,
  history factors stay neutral by design.
- **Discovery is CLI-composition only.** The MCP server composes once at start, so it uses the
  discovered set from that moment; periodic re-discovery in a long-running process belongs to the
  v0.5 daemon.
- **Carried over from v0.3:** WSL2 checks A1–A6 (deferred by the owner), live Antigravity validation
  (NXR-029), seccomp (NXR-025), launcher env via fd (NXR-026), parallel lanes (NXR-027), MCP
  engineering scope (NXR-028), the DeepSeek live key test (#13) and captured relay fixtures (#16).
