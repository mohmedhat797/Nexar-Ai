# v0.5 Nexar Mobile — readiness assessment

> **Retargeted (2026-10-01):** the owner made v0.5 **Nexar Desktop** ([ADR-021](../adr/021-nexar-desktop.md)).
> This assessment now applies to **v0.6 Nexar Mobile**; its recommendations (control-plane ADR first,
> loopback default, Windows first) still hold.

**Date:** 2026-10-01 · **Status:** assessment only; v0.5 has not been started · **Items:**
[NXR-040](../backlog/040-control-plane-adr-and-daemon-skeleton.md) (control-plane ADR and daemon),
[NXR-041](../backlog/041-nexar-mobile-pwa-shell.md) (PWA shell), and
[NXR-028](../backlog/028-mcp-engineering-scope.md) (engineering over a remote surface).

v0.5 is the first milestone that puts a network listener in Nexar. Everything before it is stdio,
subprocesses and local files. ADR-006 (local-first) and ADR-014/015 (stdio-only MCP, audited access)
were written to keep it that way, so v0.5 starts with an ADR, not code.

## 1. What v0.4 gives v0.5

- **Explainable decisions to show on a phone.** `RouteDecision` already carries tiers, factors,
  quota, cost and `configId`, and `explainRouteDecisionDetailed` is a pure function. A task detail
  view can render it without new engine work.
- **Honest quota and cost status.** `nexar resources --json` returns quota assessments and
  provenance, so a "resources" screen needs no new data model.
- **Approvals.** These exist (fail-closed, fingerprint-bound, single-use) and are the main thing a
  phone needs to act on (for example `engineering.commit`).
- **Telemetry and audit.** These are separate (ADR-020 §12, ADR-015). A daemon reuses the audit log
  for every remote call.

## 2. Decisions the owner must make (inputs to the ADR)

| Decision                         | Options                                                                                                        | Recommendation                                                                                                  |
| -------------------------------- | -------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------- |
| How the phone reaches the daemon | (a) LAN only, (b) owner's private overlay network (e.g. Tailscale or WireGuard), (c) a tunnel or relay service | (b): no public exposure and no paid relay; (a) as a fallback. (c) needs its own ADR and a security review.      |
| Daemon platform first            | Windows native, WSL2, Linux, macOS                                                                             | **Windows first** (the owner's stated priority), with the engineering plane still in WSL2 as decided in ADR-018 |
| Device credential                | per-device token (hashed at rest, like `clients.json`), or mTLS client certificates                            | Per-device token over TLS, from a one-time pairing code; reuse `@nexar/access` scopes                           |
| Scope of remote actions in v0.5  | read-only status; plus approvals; plus task submission; plus engineering                                       | Status, approvals and task submission. Engineering stays local until NXR-028.                                   |
| Voice                            | v0.5 or later                                                                                                  | Later: text first                                                                                               |

## 3. Recommended order

1. **Control-plane ADR** (NXR-040, part 1): API style and versioning, loopback default, the remote
   access model, pairing and revocation, TLS, audit, rate limits. Security review before any code.
2. **Daemon skeleton** (NXR-040, part 2): `apps/control-plane`, loopback-bound, health, task
   submit/status, approvals list/decide, event stream. It reuses the engine, `@nexar/access` and the
   approval store, and registers in `nexar doctor`.
3. **Pairing and revocation**, then any off-loopback exposure (an explicit owner action).
4. **PWA shell** (NXR-041): task list and detail (with the v0.4 explanation), approvals, resources and
   pairing.
5. Optional: periodic re-discovery and quota refresh in the long-running daemon (v0.4 discovery is
   per CLI invocation).

## 4. Security prerequisites

- A new ADR that supersedes the "no network transport" rule for this surface only. The MCP server
  stays stdio-only.
- Default bind is loopback. Off-loopback access needs TLS, device auth and an owner opt-in.
- Every request is authenticated, authorized and audited exactly once with the existing allowlisted
  audit record (no prompts, paths, content or tokens).
- Request fields never widen scopes or paths (ADR-015). Path rules still go through
  `resolveContainedPath`.
- Approvals remain the only way to authorize outward or engineering actions. A phone tap approves a
  fingerprint, never a free-form action.
- No outward executors (email, calendar, upload, push). That needs its own ADR (ADR-016).

## 5. Risks

- **First network listener.** The biggest new attack surface in the project. Mitigation: ADR plus
  review first, loopback default, a small API.
- **Windows service model.** Running a daemon on Windows (service, tray or scheduled task) differs
  from POSIX. Choose and test it early.
- **Push notifications** usually need a third-party service. Keep them out of v0.5 or behind an ADR.
- **Carried-over gaps.** The WSL2 checks A1–A6, seccomp (NXR-025) and live Antigravity (NXR-029) are
  still open. A remote surface makes the engineering plane's isolation more important, so close A1–A6
  before exposing engineering remotely.

## 6. Recommendation

Merge v0.4 after review. Then start v0.5 with the control-plane ADR only (the owner's decisions in
section 2 are its inputs), and do not write daemon code until that ADR is accepted.
