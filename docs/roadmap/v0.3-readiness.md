## 2. Recommended dependency order

```text
#17 NXR-024 OS sandbox (foundation for any write-capable agent)
        │
        ├── #16 NXR-023 Delegate Skills adapter (worktree-per-task + Nexar review gates)
        │        └── reuses relays for claude / codex / agy / pi
        ├── #13 NXR-020 DSH ACP adapter (cancel + permission round-trips → approvals)
        ├── #14 NXR-021 Codex adapter
        └── #15 NXR-022 Antigravity adapter (spike first)
```

- **#17 first.** v0.3 gives agents write access to repositories (implementation lanes). Before any
  lane runs writes unattended, Nexar needs an OS boundary: bubblewrap on Linux and sandbox-exec or a
  container on macOS. v0.2 relied on read-only defaults (Claude Code `plan` mode) and on each
  runtime's own permission model. That is not sufficient for write-capable autonomous execution.
- **#16 next.** Worktree isolation and Nexar-owned review gates are the core of the "engineering
  machine". Delegate Skills relays already give per-CLI adapters (claude, codex, agy, pi) with a
  stable `result.json`, which reduces the work for #14 and #15.
- **#13 (ACP)** maps DSH permission requests onto the v0.2 approval framework (`@nexar/approvals`).
  This is the first real approval _consumer_ besides the CLI, so it must follow ADR-016 (bind the
  exact action; deny by default).
- **#14 and #15** can be implemented either as native adapters or through the Delegate Skills lane.
  Decide in the #16 ADR to avoid duplicate paths.

## 3. Security prerequisites

1. **OS sandbox (#17):** filesystem limited to the task worktree; network off by default; no access
   to `~/.ssh`, `~/.config`, or credential stores. Nexar's realpath policy (ADR-012) stays the
   first gate, and the sandbox becomes the second.
2. **Git safety:** agents never push. Nexar owns commits, and only after gates pass. This matches the
   development-time rule in ADR-009, now applied at product time.
3. **Approval classes:** "write in worktree" is low risk and auto-approved inside the sandbox;
   "push / open PR / install dependency" is high risk and needs human approval through
   `@nexar/approvals`.
4. **Process trees:** v0.2 fixed DSH process-group termination. Apply the same pattern to every new
   subprocess adapter (Codex, `agy`, relays).
5. **Credentials:** subscription runtimes (Codex / ChatGPT, Antigravity / Google) must authenticate
   through their own CLIs. Nexar never reads their tokens. API keys stay env references.
6. **Audit:** each engineering lane run gets audit and telemetry records (resource, worktree, gate
   results, commit SHA if accepted).

## 6. Expected acceptance criteria (summary; full criteria live in each issue)

- **#17:** an agent cannot read or write outside its worktree or reach the network unless allowed.
  Escape tests (symlink, absolute path, `..`, network) fail closed. It covers all subprocess adapters.
- **#16:** `nexar run --lane <name>` creates a worktree and dispatches to the lane's implementer.
  Nexar runs the repository gates, shows the diff, and commits only on approval. Relay results map to
  `ExecutionRecord`.
- **#13:** ACP adapter with cancel. DSH permission requests become Nexar approval requests (exact
  action binding). Contract tests use a fake ACP agent, and the live test is opt-in.
- **#14 and #15:** native or relay-based adapters with fake-binary contract tests, env scrubbing,
  process-group termination, opt-in live tests, and `nexar doctor` detection.
- All work items: offline CI, no paid calls, boundary rules extended for any new upstream package,
  and ADRs for the sandbox and the lane model.

## 7. Risks to watch

- Codex and DSH release roughly weekly: pin exact versions and add upgrade playbooks.
- The Antigravity headless interface is unknown and could remove #15 from v0.3.
- macOS sandboxing is harder than Linux. Keep it as a stretch goal if the owner works on macOS.
- Cost: engineering lanes consume far more tokens than v0.2 documents. Consider pulling v0.4 quota
  tracking (#18) earlier if subscription limits become binding.

## 8. Recommendation

Start v0.3 with a short **sandbox and lane-model design phase**: one ADR each for #17 and #16. Run
the Antigravity spike in parallel. Then implement #16 on Claude Code (already verified live), and
add Codex, DSH ACP, and Antigravity as independent parallel lanes. Get the owner's decisions from
§5 before starting any live test.
