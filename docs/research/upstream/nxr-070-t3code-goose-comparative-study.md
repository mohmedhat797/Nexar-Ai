# NXR-070: Nexar, T3 Code and Goose comparative study

Status: architecture research complete for review; implementation NOT STARTED. Evidence snapshot: 2026-10-08. Companion decisions are [Proposed ADR-029](../../adr/029-resource-fabric-provider-runtime-v2.md), [the implementation blueprint](../../architecture/nxr-070-resource-fabric-implementation-blueprint.md) and [NRC v2 design](../../architecture/nxr-070-nrc-v2-resource-intelligence.md).

## Executive recommendation

Evolve Nexar's existing resource system into a Resource Fabric. Adopt T3's explicit provider-instance identity and scoped lifecycle patterns, adapt Goose's ACP boundary for optional delegated agent runtimes, and retain Nexar's Registry, Strategy, NRC, Control Model Gateway and Intelligence Execution Bridge. The differentiator is trustworthy resource allocation across engines, not launching more providers.

A factory/instance/runtime graph is more accurate than a chain from provider to account to session to inventory. One instance can expose several runtimes in several environments. Each binding has independent authentication and negotiated capabilities. Sessions belong to executions; discovery must not require opening a session by default.

The first slice projects current connections and inventories into this graph without changing authentication or execution. Existing IDs, pins, model-turn routes and native agents remain usable. ACP and multi-account login follow separate evidence gates.

## Current Nexar domain map

```text
Provider family metadata
  -> ProviderConnection (method, auth class, machine, support, enabled)
  -> ProviderRuntimeIdentity (connection + runtime + route + machine)
  -> bounded ProviderInventorySource / snapshot
  -> fresh inventory materialization -> ResourceDescriptor + ResourceState
  -> Resource Registry -> Resource Strategy -> NRC allocation
  -> Control Model Gateway (pinned model-turn) / Intelligence Bridge (workers)
  -> integration adapter -> OpenWorker or DSH / native execution

OperatingSession + context@1 remain canonical across the above.
Telemetry history supplies measured facts to the pure routing policy.
```

## T3 Code findings

### Drivers, instances, accounts and environments

VERIFIED: ProviderDriverKind and ProviderInstanceId are distinct branded keys (T1). Factories create scoped instance objects exposing adapter/auth/text/catalog facets (T2); registry reconciliation decodes config, represents unavailable instances and closes scopes (T3). UI and core still have provider-specific configuration and installation behavior. A driver boundary reduces conditionals; it does not eliminate all provider-specific UX.

Multiple instances can coexist architecturally. Actual account isolation depends on credentialBinding, runtime home and a driver's support declaration (T2–T5). Two labels do not prove two accounts. INFERRED: Nexar should preserve this separation while recording an independent principal assertion and runtime environment. UNVERIFIED: every T3 driver/Windows runtime genuinely isolates credentials.

T3 merges process environment with instance overrides and expands runtime homes (T4). Nexar should adopt scoped homes only through owner-approved official/native configuration, with a minimal child environment. Raw sensitive env values in general config, shared external credentials, and reading Cursor keychain tokens (T16) are explicitly rejected.

### Inventories, capabilities and usage

VERIFIED: Codex's runtime probe obtains account state, paginated native models and optional rate-limit windows (T11, T15). Claude's manifest/version/bundled/custom model catalog (T12) has a different authority. “Available” must carry its source: a manifest entry is not proof of account entitlement. Native Codex inventory cannot be reused as ChatGPT Responses inventory.

T3 models rich session/thread/turn/tool/approval/context capabilities and distinguishes native enforcement from client-boundary enforcement (T6, T13). Nexar should negotiate facets rather than infer engine compatibility from a provider name. Current model and reasoning options are session/runtime state, not permanent resource identity.

Usage contracts separate reported counts, pricing estimates and subscription API-equivalent cost (T14). API-equivalent cost is not the owner's subscription bill. Native transcript collection reads and caches provider-specific records (T18); initial Nexar telemetry should record its own executions. External history ingestion requires a separate owner/privacy decision.

### Sessions and provider switching

VERIFIED: adapter contracts separate provider sessions from native threads; orchestration contracts also represent app-level state (T6, T13). The transition policy can reuse, switch at a next turn, restart with native resume, create a portable handoff or reject (T7). Tests explicitly cover account-identity changes, driver changes and missing transition classifiers (T8).

Cross-provider transitions use portable context rather than transferable opaque reasoning state. Handoff budgets preserve source attribution and bounded items; the unknown-context-window fallback is an estimate, unsuitable as an authoritative Nexar capacity (T9). Delivery persistence before injection and uncertain-delivery handling are useful reliability patterns (T10). Nexar still forbids switching an active Control loop even if an upstream runtime permits model changes.

## Goose findings

### ACP runtime and subscription agents

VERIFIED: Goose wraps external Claude, Codex and Pi ACP binaries (G5–G8). The wrappers describe native subscription/API auth handled by those runtimes, not by Goose's resource policy. This is source support for integration shape, not verification of Windows installation, vendor entitlement or account isolation.

The ACP client negotiates protocol V1, sessions, prompt/update handling and optional load/close. Library versions differ from wire versions: Goose manifests declare agent-client-protocol 2.2.0 and schema =1.9.1, while the wire handshake uses V1. These version numbers are not interchangeable. Installation/discovery can create a live native session in this implementation; Nexar must distinguish passive discovery from session-starting validation.

The shared Provider trait allows complete/stream/session/context facets (G1). AcpProvider's stream ignores caller system/tools and runs the external agent's loop (G8). **An ACP agent-run is not automatically a normalized model-turn port.** Default no-op resume is not negotiated support. Nexar should retain composed ports rather than copy this giant interface.

### MCP, permissions, models and sessions

VERIFIED: MCP stdio and supported HTTP configurations are converted and HTTP is capability-filtered; SSE/socket variants and other extension forms are not universally forwarded (G8). This is interoperability, not permission confinement. Nexar's current stdio-only network/security rule remains authoritative; HTTP passthrough is deferred pending a separate ADR.

Wrapper modes are provider-specific: Claude Auto can map to bypassPermissions; Codex Auto to full access (G5–G6). Reject those as Nexar defaults. Preserve deny-by-default, action-bound approvals, grants and OS containment (N21). External native tool events must not be redispatched as duplicate Nexar tool calls.

Model discovery in the inspected client requires a model-category select config option; available/current choices come from the runtime (G8). Official ACP treats category as a UI hint, so future Nexar code should negotiate the actual option ID and support an absent model selector. Legacy/current config dialect differences need fixtures.

Load/resume is optional and runtime-dependent. Goose's ACP server forks its own stored session (G10); this does not establish external Claude/Codex client fork support. Session release/process cleanup is inspected; graceful cancellation acknowledgements and interrupted native write recovery remain conformance spikes. Do not infer completed cancellation from a UI stop action.

### Context and telemetry

Goose's handoff memo bounds chronology, preserves tool exchange pairs and prunes older outputs (G9). This is not comprehensive secret redaction. Its client can retry a rejected memo with the bare prompt before updates (G8); Nexar should reject silent loss of required constraints and require an explained recovery decision.

Optional token/cost data exists (G11–G13). Tokenizer fallback fills missing token fields without equivalent per-field authority tags (G12). Nexar should preserve reported versus estimated provenance through aggregation. ACP completion usage does not guarantee cache counts or subscription headroom.

## Target, migration and open questions

Target: instances/config intent plus runtime definitions and environment bindings produce evidenced inventories and executable resources. Observations build Resource Profiles; pure policy validates/ranks them; NRC decisions drive existing gateways. Drivers normalize vendor details before anything reaches NRC. Session bindings remain private execution state alongside canonical Nexar sessions.

Migration is additive. Start with read-only compatibility projection, then isolated configuration, runtime bindings, inventories, an optional ACP worker, measured observations and enriched NRC, followed by instance UX and handoff. Legacy pins/resources survive aliases; no destructive credential relocation. Exact phases, rollback and acceptance are in the blueprint.

Open questions remain UNVERIFIED: native multi-account isolation on Windows/plane; documented account catalog authority and drift for each route; external ACP model/config dialects; real resume/fork/cancel guarantees; ACP MCP trust/confinement; Antigravity ACP availability and vendor terms; subscription quota interfaces; end-to-end review independence; benchmarks appropriate to the owner's tasks. Source support is not live acceptance.
